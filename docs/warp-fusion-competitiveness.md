## 1. 品类界定：先说清它是什么、不是什么

错位比较是竞争力讨论中最常见的失真来源。WarpFusion 的准确定位：

**它是**：一个以**跨多条事件、跨时间窗口的模式匹配**为内核的实时关联计算引擎。输入结构化事件流，输出满足关联条件的、可解释且带评分的结果。单二进制、零外部依赖。

**它不是**：

- 不是通用分布式流计算平台（无分布式协调、无 checkpoint）；
- 不是数据仓库或分析型查询引擎（不做交互式分析、不做行保留聚合）；
- 不是 SIEM 平台（不提供存储、检索、可视化、案件管理）。

因此本文的对照分两条线展开，各自与**真正同层的对手**比：

| 对照线 | 对手 | 比什么 |
|---|---|---|
| **引擎算力** | Flink OSS、阿里 VVR、RisingWave、Feldera | 吞吐、内存、架构归因 |
| **语言表达力** | YARA-L 2.0、EQL、Sigma、SPL、KQL | 检测语义覆盖度、工程治理原语 |

## 2. 竞争力主线一：引擎算力

### 2.1 方法论先行

任何性能对照，口径比数字更重要。本次对照的条件与残余不对等如下：

| 维度 | WarpFusion | Flink OSS | 阿里 VVR |
|---|---|---|---|
| 版本 | v2.0.7 | 1.20.4 | vvr-11.5-jdk11-flink-1.20 |
| 数据规模 | 100,000,000 | 100,000,000 | 100,000,000 |
| 计算资源 | Linux 8 核（**与 VVR 同型号云服务器**） | 3×ecs.g6a.xlarge = 12 vCPU / 48GiB | 8 CU ≈ 8 vCPU / 32GiB（托管集群） |
| Sink | 本地文件（blackhole 等价） | Blackhole | Blackhole |
| 指标 | 哨兵 EPS = Σn /（max emit − min start） | RPS = 输入量 / 用时 | RPS = 输入量 / 用时 |

**残余不对等（必须承认）**：计算资源计量口径不同（8 核 vs 8 CU；OSS 为 3×12 vCPU）；OSS 为三节点集群而 WarpFusion 为单机。**结论作量级参照，不作为生产 SLA 承诺。**

### 2.2 对照结果（NEXMark Q1–Q22）

| 对照基线 | 几何平均 | 算术平均 | 逐查询区间 | 胜出 |
|---|---|---|---|---|
| **Flink OSS** | **24.3×** | 44.7× | 6.06× – 231.49× | 20/20 全面领先 |
| **阿里 VVR** | **6.8×** | 10.1× | 1.76× – 39.98× | 20/20 全部达 VVR |

参照系：白皮书口径下 VVR 相对 OSS 自身的提升为 **3.24×**（本报告按 20 个查询复算几何 3.57×）。即 WarpFusion 是在一个已做过企业级优化的商用引擎之上再领先一个身位。

**逐查询节选**（条/秒）：

| Query | 语义 | WarpFusion | OSS | VVR | vs OSS | vs VVR |
|---|---|---:|---:|---:|---:|---:|
| q1 | 无状态投影 | 16.85M | 1.75M | 4.38M | 9.62× | 3.85× |
| q7 | 时段最高出价（match 序列） | 9.29M | 0.08M | 0.30M | 116.74× | 31.03× |
| q9 | 中标出价（asof join） | 7.96M | 0.04M | 0.38M | 185.08× | 21.22× |
| q11 | 会话窗口统计 | 10.85M | 0.24M | 0.69M | 44.36× | 15.84× |
| q19 | 拍卖 Top-10（stats） | 7.86M | 0.17M | 1.05M | 46.08× | 7.48× |
| q20 | 展开关联（snapshot join） | 17.27M | 0.07M | 0.43M | **231.49×** | **39.98×** |
| q14 | 时间戳换算（Calculation） | 8.80M | 1.45M | 5.00M | 6.06× | **1.76×** |

**为何头条用几何均值**：逐查询倍数分布严重右偏——约一半查询落在 1.76×~7.15× 的典型区间，而 q7/q9/q11/q16/q20 等形成长尾。对"提速倍数"这类比率量，几何均值满足乘性对称（A/B 的几何均值与 B/A 互为倒数，算术均值做不到）且抗离群，回答的是"随便挑一个查询大概快多少倍"。算术均值（10.1×）被长尾抬高约 1.5×，仅作上限语境。

### 2.3 架构归因：优势来自砍掉了什么

| 杠杆 | 砍掉了什么 |
|---|---|
| **列式批式向量化** | 逐事件对象分配 + 解释器分发 |
| **数据零拷贝** | Event → Record → DataRecord 多层拷贝 |
| **内存精确控制** | 窗口数据仅过期且被下游全部消费后才释放；预读总量设字节上限 |
| **Rust vs Java** | JVM GC 停顿 |
| **规则即规划** | 运行期逐事件解释（Stats / Match 编译期定型为执行计划） |

其中"内存精确控制"是设计纪律而非调优技巧：释放条件是**既已过期、又被所有消费者确认消费**，配合预读字节预算，使内存占用可预测、可规划，而非"跑着看"。

### 2.4 与其他现代引擎的量级参照

⚠ **本小节为公开宣称的转述，非本仓库同方法论实测**，仅作量级定位，不应与上表并列引用：

- **Feldera**（增量计算）：公开宣称相对 Flink 约 **2.2×**；
- **RisingWave**：公开宣称 **2–10×**，但其基准方法存在争议。

二者相对 Flink 属 2–4× 量级的改进；WarpFusion 在同方法论下为 **24.3×（几何，vs OSS）**。

### 2.5 已知问题与边界（一并公开）

本节各项**性质不同，不可混为一谈**——尤其要区分"相对 Flink 的不足"与"内部待优化项"：

| 性质 | 项 | 说明 |
|---|---|---|
| **相对 Flink 的能力缺口** | 无 exactly-once / checkpoint | 当前 best-effort，可靠性在路线图。**这是引擎能力维度上唯一落后于 Flink 的项**（分层说明见 §6）。 |
| **最弱优势项**（仍领先，非短板） | q14 相对 VVR 仅 1.76× | ⚠ 注意性质：这是全表**最弱的一项，但仍是 1.76× 领先**（vs OSS 为 6.06×）。它是"最弱的优势"，**不是"短板"**。Calculation 类、字符串处理重，瓶颈在引擎行式 cell 求值，已列为通用能力独立立项。 |
| **内部已知问题** | q18 内存（RSS 27.9GB @100M） | 状态窗随数据量线性增长。**无 Flink 同口径 RSS 对照数据**——属待优化项，不能据此判定劣于 Flink。 |
| **预期内特征** | q5 / q18 规模退化（30M→100M 为 0.58× / 0.34×） | 由窗口状态随数据量增长驱动，属状态型查询的预期表现，**非 bug**。 |

> **判别原则（弱势项 = 该维度上 WarpFusion 低于 Flink；"自己内部相对最弱的项"不算弱势项）**：只有"对手有而我们没有、或对手做得更好"才算**相对短板**。
> - 仍领先但领先幅度小 → **最弱优势项**（如 q14）
> - 无对照数据的内部问题 → **待优化项**（如 q18 内存）
> - 对手同样没有的能力缺口 → **不属于相对该对手的短板**（如分项评分/基线，Flink 亦无）
>
> 三者对外表述不可混淆：把"最弱的优势"说成"短板"会自我削弱；把"内部问题"说成"竞争劣势"则失真。

**引用口径**：本文全部吞吐数字均为 **NEXMark 单查询口径**——Linux 8 核、**blackhole 汇（不落告警）**、2026-08-27 权威跑批。

> ⚠ **目前没有多规则混合负载的近期实测数据**。历史上存在一次混合负载测量（6 条规则、macOS 4 并发），但测量于 2026-08-10，早于 08-16 落地的批式向量化等重大吞吐优化，**已过时且未复测，故不在本文引用**。
>
> 需要强调：真实部署若规则会大量触发告警并落 sink，吞吐会**显著低于**上表的 blackhole 口径。评估容量时应按自身告警率实测，不可直接套用。

### 3.3 🟡 两项规划能力——真实状态说明

专业读者最容易被"已支持"误导，以下两项在部分旧文档中标注乐观，**此处如实说明**：

**(1) 分项可解释评分 `-> score { item @ weight }`**

- **当前实际**：仅支持单通道 `-> score(expr)`——规则产出单一数值分，分项权重与 `score_contrib` 明细**尚未实现**；
- 规划中的 `hit(cond)`（布尔条件映射为评分权重）**亦未落地**，当前以 `if/then/else` 替代；
- 依赖这两项的**跨规则评分累加**同属规划态。

**(2) 基线偏离 `baseline(expr, dur, method)`**

- **函数可用，但语义受限**：源码核查确认 `dur` 参数**在实现中被忽略**（`eval/mod.rs` 只读 `args[0]` 与 `args[2]`），实际为"实例启动以来的累积统计量"而非"过去 N 天"；状态键不含 `dur`；
- **无持久化**：状态挂在 match 实例上，实例淘汰即从零冷启动（`state.rs`）；
- **完整设计已定稿但未落地**：`wp-reactor/docs/design/baseline-online-design.md`（v2.2）给出完整方案——五原语复用的基线生成（`stats` 窗口产出 `BaselineRecord` → `yield` → 独立持久存储）、消费侧 `baseline(近期窗口, 周期, 方法, 值)` 签名、同比/环比周期支持、半衰期加权合并，且已确认"能否进 yield"等实现疑点。
- **对外谨慎口径**：在落地前，不建议将"内置在线基线"作为选型的决定性依据。

### 3.4 WFL 独有能力（五种 DSL 均无对应）

**已落地**：OR 分支时序、双阶段匹配、一等实体声明 `entity()`、数值风险评分 `-> score()`、Join 时点语义一等化（`snapshot` / `asof within`）、规则级资源预算 `limits`、输出契约版本化 `yield target@vN`、Conformance 门禁、`yield` 统一输出、风险等级派生（`score` → `level_map`，可版本化）、三文件分离、L1/L2/L3 能力分层、声明式窗口统计 `stats<dur> [group by] { agg as label }` 与 `tier` 分档、跳窗 `hop(size, slide)`、反连接 `join ... anti`、受控/延迟连接 `emit at` + `reduce`、哈希族（`md5`/`sha1`/`sha256`/`hex`/`stable_id`）、`cidr_match`、多精度当前时间、`object{}`/`array[]` 与 `merge`、`top_ties(N)`、规则级 `let`、`external()` 外部服务调用。

**规划中**：分项可解释评分、`hit(cond)`、跨规则评分累加、基线的完整语义与持久化。

### 3.5 与 SPL / KQL 的差距收敛

早期 WFL 相对 SPL/KQL 在聚合能力上差距明显，经 `fixed`、`conv`、`|>` 及行为分析扩展后：11 项对照维度中 **7 项已消除、3 项大幅缩小、1 项（行保留聚合）有意不做**。字符串与时间函数族在 v2.2 补齐 20+ 个函数后继续收敛，与 SPL Top50 高频函数对齐率达 **100%（50/50）**。

**残余差距的本质**是"检测 DSL vs 通用查询语言"的设计取舍，而非能力缺失：SPL 仍保有 200+ 函数、无限管道、`eventstats`；WFL 有意把这些交给下游 SIEM，把预算投向检测语义与工程治理原语。

## 4. 竞争力主线三：工程治理与正确性

这一条决定了"能不能上生产"，是专业读者与营销材料关注点的分水岭。

| 机制 | 说明 |
|---|---|
| **三文件职责分离** | `.wfs`（数据 schema）/ `.wfl`（匹配逻辑）/ `.toml`（运行配置），数据工程师、分析师、SRE 各改各的 |
| **Conformance 门禁** | `test`（内联契约测试）+ `shuffle`（乱序鲁棒性）+ `scenario verify`（场景对拍）前置为发布门槛 |
| **输出契约版本化** | `yield target@vN` + `meta.contract_version`，下游字段演进可灰度、可回滚、可审计 |
| **规则级资源预算** | `limits { max_memory; disk_provider; max_disk }` 阻断高基数状态膨胀 |
| **能力分层** | L1（MVP）/ L2（增强）/ L3（高级 + feature gate），避免首版认知过载 |
| **热加载** | `wf reload`，规则变更不重启引擎 |
| **Join 时点语义** | `snapshot` / `asof within` 一等语法，消除在线与回放在维表取值时点上的语义漂移 |
| **确定性生成与对拍** | `wfgen` 同一 count+seed 字节级确定；`wfl verify` 逐字段对拍 |

正确性现状：30M 规模 oracle 对拍中 Q4/Q9 **完全一致**；已知差异为 Q12（fixed+close 尾桶，已知差异）与 Q19（stats oracle 未接入）。

**成熟度**：上表所列除 `dmdb`（达梦，位于 `wp-connectors-labs`，ODBC，未进默认特性）外，均**已实现并带单元测试**；各连接器的集成测试需真实实例（`external_integration` 特性门控），与 Kafka（`SKIP_KAFKA_INTEGRATION_TESTS`）同为连接器的通用测试模式。

> **更正一处上游文档滞后**：`wp-connectors` 的 README 曾把 `elasticsearch` / `clickhouse` 标注为 placeholder。2026-08-30 代码核查显示**该标注已过时**：ES sink 完整实现了 `_bulk` API（reqwest + basic auth + NDJSON + `BulkResponse` 逐条错误解析，770 行源码、**10 个单元测试**）；ClickHouse 899 行、**30 个单元测试**，**并非占位**。上游 README 已同步修正（连接器表、Features 表、项目结构共 4 处，并补入此前遗漏的 PostgreSQL / UDP / count）。

**架构上值得注意的是分工**：日志的**接入与解析归一化**由上游 WarpParse 承担（WPL / OML 适配器，覆盖 Windows EventLog、EDR 等原始日志源，产出与 `.wfs` schema 对齐的类型化字段），再通过 **Arrow IPC over TCP** 送入 warp-fusion 做关联检测。这条链路的价值是**全程免解析、零反序列化、类型保真**——数据以 Arrow `RecordBatch` 形态一路流到规则引擎，不像传统管道那样在每一跳反复序列化。

**诚实的对照**：Flink 十年积累了**数百个**社区 connector（这是真实护城河）。WarpFusion 侧通过 `wp-connectors` + `wp-core-connectors` 已覆盖**消息队列、关系库、OLAP、搜索 / 日志系统、时序、HTTP 与基础 I/O**等主流通道，可支撑端到端落地。差距集中在**广度**（尤其 SaaS 与小众数据源），而非"有没有体系"；且 Arrow 原生链路在已覆盖的通道上省掉了逐跳反复序列化的开销。

## 5. 综合使用成本（TCO）

| 成本项 | Apache Flink | WarpFusion |
|---|---|---|
| 硬件 | 至少 2–3 节点（JobManager + TaskManager + Kafka）+ 磁盘状态存储 | 1 台 8GB 节点起步 |
| 中间件 | Kafka + checkpoint 状态存储 | 零外部依赖 |
| 运维人力 | 专职流工程师维护集群、调 checkpoint / state | 单二进制，普通运维即可 |
| 开发人力 | 数据工程师写 Java / SQL，每条规则一次 job 生命周期 | 分析师写 WFL，热加载生效（AI 可辅助生成，见 §5.2） |
| 规则迭代 | AI 可加速**编写**，但**验证 + 编译 + 部署 job** 的周期不变 | 编写 → 内联契约测试 → 热加载，端到端链路最短 |
| 授权 | 开源免费；托管服务按小时计费 | ELv2：企业内部自用免费，转为对外服务需商业授权 |

在**单机可承载、千条规则**这一常见量级下，Flink 的综合成本通常为数倍：资源预算差 2–3 倍，运维与开发需不同类型的人，规则迭代的**端到端周期**（含验证与部署）也更长。

> ⚠ **一处已失效的旧论证**：早期文档称"规则编写成本是差距最大的单项（WFL 数十分钟 vs Flink 以天计）"。**AI 辅助编码普及后该说法不再成立**——编写环节对双方都被大幅压缩。修正后的论证见 §5.2。

### 5.1 量级估算：十万 vs 百万

> ⚠ **以下为按公开市场行情的粗算，非报价，也未含一次性迁移/学习成本。** 单位成本假设全部列在表后，**请按自身地区与实际单价替换后重算**。本节的结论依赖的是**成本结构**（人力占大头），而非下列具体数字。

**场景设定**：千条检测规则、峰值十万级 EPS、秒级响应、7×24 运行的中等规模实时检测平台。

| 成本项（年度） | Flink 自建 | WarpFusion |
|---|---|---|
| 计算资源 | 4 × 8C32G（JM + 3 TM）：**8 万** | 1 × 8C32G：**2 万** |
| 消息中间件 | Kafka 3 节点：**6 万** | **0**（直连，无需 Kafka） |
| 状态存储 | 对象存储 / checkpoint：**1 万** | **0**（无 checkpoint） |
| 运维人力 | 流平台工程师 0.5 FTE：**20 万** | 普通运维 0.1 FTE：**3 万** |
| 规则开发 | 数据工程师 0.5 FTE：**20 万** | 分析师 0.3 FTE：**9 万** |
| **年度合计** | **约 55 万/年** | **约 14 万/年** |
| **3 年 TCO** | **约 165 万** | **约 42 万** |

**量级结论**：Flink 自建路线落在**百万量级**（3 年 TCO 约 150–200 万），WarpFusion 落在**十万量级**（3 年约 40 万），**差距约 4 倍**。

**假设基准（可调，替换后重算即可）**：

| 参数 | 取值 |
|---|---|
| 8C32G 云服务器 | 2 万 / 台 / 年（包年） |
| 流平台工程师 | 40 万 / 年（综合人力成本） |
| 数据工程师 | 40 万 / 年 |
| 安全分析师 | 30 万 / 年 |
| SRE / 运维 | 30 万 / 年 |

**三条结构性结论（比上表数字更稳健）**：

1. **人力远大于硬件**——Flink 侧硬件仅占约 27%，人力占约 73%。真正的降本杠杆是**摆脱对专职流工程师的依赖**，而不是省服务器。
2. **规则迭代频率放大差距**——规则改得越勤，Flink 每次 job 生命周期的开销被摊得越薄。若规则每月变更 10 次以上，4 倍差距会进一步拉大。
3. **规模越小，固定开销越难摊薄**——在十万级 EPS 这一档，Flink 集群的 JobManager + Kafka + 状态存储是刚性支出，不随负载下降。

### 5.2 AI 辅助规则开发：差距被压缩了，但没消失

AI 编码助手已重塑规则开发方式。判断一门语言对 AI 是否友好，关键不是"语料多不多"，而是三个要素：

| 要素 | 对 AI 生成的影响 | WFL | Flink（Java / SQL） |
|---|---|---|---|
| **语言表面积** | 越小，越易一次生成正确 | 一条规则**几行**声明式代码 | 数百行 Java DataStream 或嵌套 SQL |
| **语义明确度** | 越显式，歧义越少 | 语义显式（`entity` / `score` / `match` 各有明确语义与校验） | 大量隐式约定（状态、水位、并行度、序列化） |
| **验证反馈速度** | 越快，越能"生成→验证→修正"闭环 | 内联 `test`，**秒级**验证命中/未命中 | 需起环境、造数据、部署 job |

**结论：WFL 的简洁与强语义在 AI 时代是放大器，而非障碍。** 表层看，WFL 是私有语言、预训练语料稀少；但实践上，语言本身足够小且语义足够显式，配合随包提供的完整语法指引，AI 能稳定地产出正确规则——并且产出后能被**立即验证**。相比之下，Flink 侧即便 AI 生成了数百行代码，"能否正确运行"仍要等到 job 部署之后才知道。

**验证闭环才是真正的分水岭**（AI 无法替代的部分）：

| 环节 | AI 能否替代 | 差异所在 |
|---|:---:|---|
| **编写** | ✅ 能 | WFL 因简洁/语义化，AI 生成效率尤其高 |
| **验证** | ❌ 不能 | WFL 有**内联契约测试**（规则文件内直接写 `test ... for ...`）+ `wfl replay` + `wfl verify` 对拍 + `wfgen` 生成带命中/近失/未命中三类样本；Flink 侧验证一条 job 仍需起环境、造数据、跑起来 |
| **部署 / 生命周期** | ❌ 不能 | Flink 每条规则一个 job，改动需编译 + 部署 + 重启；WarpFusion 热加载生效 |
| **正确性责任** | ❌ 不能 | AI 生成的检测规则出错是**静默**的（漏报 / 误报不报错）。**AI 生成不等于免验证**——产出必须经过可回归的门禁 |

**支撑 AI 生成的基础设施（已就绪）**：

| 手段 | 现状 |
|---|---|
| **`wf-skills` AI 技能包** | 已发布，安装进 `~/.claude/skills` 或 `~/.codex/skills`。含 **6 个技能**（共 1368 行指引）：`wf-wfl-authoring`（347 行，覆盖语法、schema 对齐、规则不触发与编译错误排查）、`wf-wfs-authoring`、`wf-config-authoring`、`wf-data-governance`、`wf-test-pipeline-debugging`、`wf-perf-bench-verification` |
| **`wf-rules` 规则库** | 18 条真实 `.wfl` 规则，可作为 few-shot 语料 |
| **编辑器与语言服务** | `tree-sitter-wfl` 语法定义 + Zed 语法高亮 + LSP（诊断 / 跳转 / 补全），让 AI 产出在编辑器内即时校验 |

**一句话**：AI 把"编写"变成了低成本动作，于是**验证与上线**成为规则迭代周期的决定项——WFL 在这两处（内联契约测试 + 热加载）具备结构性优势，而简洁、强语义的语言特性又让它成为 AI 生成规则的高效载体。前提是：生成的规则**必须**跑 `wfl test`。

## 6. 选型决策：什么时候选它，什么时候不要

### 适选

- 负载为**单机可承载的量级**，且需要**跨事件 / 跨窗口关联**（而非单条过滤）。实测参照：NEXMark **单查询**口径，8 核 **200 万–3100 万 EPS**（2026-08-27）；注意该口径为 blackhole 汇不落告警，告警密集场景需按自身告警率实测（见 §2.5）；
- 规则**高频迭代**，且改动需要自带测试与热加载；
- 需要**时序链、缺失检测、实体建模、可解释评分**等检测语义，现有查询语言表达吃力；
- 团队**没有专职流计算工程师**，或不想为这个量级养一个 Flink 集群。

### 不适选（请诚实回避）

| 场景 | 原因 |
|---|---|
| **多节点高可用 / 分布式容错** | **真正的边界在此，不在吞吐**。单机吞吐并非瓶颈——8 核实测已达 **200 万–3100 万 EPS**；WarpFusion 当前无 exactly-once / checkpoint、无分布式协调，这三项是 Flink 的主场 |
| 要求 exactly-once / checkpoint | 当前 best-effort，能力未落地 |
| 交互式分析、行保留聚合 | 有意不做，交下游 SIEM |
| 依赖**数百种数据源**的开箱 connector | WarpFusion 有注册表式 connector 体系（可外部注册扩展），`wp-connectors` 已覆盖 **Kafka、MySQL、PostgreSQL、Doris、Elasticsearch、ClickHouse、VictoriaLogs、VictoriaMetrics、Prometheus、HTTP、UDP** 及 file / tcp / syslog 等主流通道；但**广度**远不及 Flink 十年积累的数百个社区 connector（见 §4.1） |
| 依赖现成的社区规则库 | 目前**无社区规则库**，规则需自行编写；可考虑支持 Sigma 规则导入编译为 WFL |
| 需要通用数学计算（三角函数等） | 函数库聚焦检测场景 |

### 关于核数扩展（一个常见误解）

8 核已达千万级 EPS，于是容易推出"堆到 32 核还能线性翻"。这需要按查询类型分开看，依据是 8 核机的 CPU 占用实测：

| 查询类型 | CPU 占用（8 核实测） | 真实瓶颈 | 加核是否有效 |
|---|---|---|---|
| 无状态投影 / 过滤（q1/q2/q3/q8/q10/q14/q21/q22） | ~100% avg | **单连接读链供给**，非算力 | **有限** —— 瓶颈在读链不在核数 |
| 重查询（窗口 / join / 状态型） | 400%+ avg | 算力 | **有效** —— 多核已被充分占用 |

**结论**：状态型与 join 类负载，加核是有效路径；无状态负载当前受单连接读链约束，加核的边际收益取决于读链是否先行打通——这是引擎级改进项，不是配置问题。

> ⚠ **仓库目前没有 32 核的实测数据**。上表为基于 8 核 CPU 占用特征的推断，**不作为容量承诺**。若需 32 核的容量结论，应先以同方法论跑一遍基准再对外引用。

## 7. 竞争态势总结

| | 有利 | 不利 |
|---|---|---|
| **内部** | **优势**：同方法论下量级领先的算力（vs OSS 几何 24.3×）；五种检测 DSL 均无的语言层检测/治理原语；单二进制零依赖带来的 TCO 优势；规则自带测试闭环<br>**短板（严格限定为"相对 Flink 的不足"，仅两项）**：① 无 exactly-once / checkpoint；② 生态广度（connector 种类、社区规则库）<br>**内部待优化（非相对 Flink 的不足）**：q14 为最弱优势项（仍领先 1.76×）、q18 内存与规模退化——见 §2.5<br>**相对 SIEM 平台的不足（非 vs Flink）**：分项可解释评分、内置基线尚未落地（Flink 同样没有，故不计入 vs Flink 的短板） | 生态与信任度落后于十年积累的 Flink 与平台化 SIEM |
| **外部** | **机会**：单机可承载的中等规模实时检测，长期被"上流计算太重、上 SIEM 表达不够"两头挤压；**AI 时代 WFL 因简洁/强语义/可秒级验证，成为规则生成的高效载体**（§5.2） | **威胁**：Flink 系持续优化；SIEM 平台通过 ML 模块补齐检测语义；Sigma 社区规模（5000+ 规则）构成分发侧壁垒 |

**一句话竞争定位**：

> 在"单机可承载、需要跨事件关联、规则高频迭代"这个区间，WarpFusion 提供的是**十倍级算力冗余 + 检测语义最完整的一门语言 + 数倍低的综合成本**；它不试图在分布式容错、通用分析、生态规模上竞争，这些边界在本文第 6 节已明确列出。
