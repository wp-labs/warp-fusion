# WarpFusion：把实时关联计算，压进一个二进制

> 单条事件只能告诉你"发生了什么"，回答不了"这些事件放在一起意味着什么"。
> WarpFusion 是一套用声明式规则语言回答后一个问题的实时关联计算引擎——Rust 编写，单二进制，零外部依赖。

---

## 一、从一个回答不了的问题说起

设想一条再普通不过的安全规则：**同一 IP 在 5 分钟内登录失败 3 次，随后发起端口扫描**。

拆开看，它同时跨越了三个维度：

- **跨数据源**——登录日志和网络流量要放在一起看；
- **跨时间窗口**——"5 分钟内"是个时间约束，引擎必须记得住刚才发生了什么；
- **跨步骤**——失败在前、扫描在后，顺序不能乱，中间还可能要求"始终没有成功登录"。

这类需求从不局限于安全。**风控**要识别"短时多笔异地交易"；**运维**要判断"错误率突增且伴随延迟抬升"；**IoT** 要发现"设备温度持续偏离自身常态"。它们共同的要求是：引擎得**缓存历史、维护有状态窗口、执行模式匹配**。

问题在于，现成工具各有各的代价。上 Flink 这类通用流计算，你要为这个量级付出集群 + Kafka + 每改一条规则重走一遍 job 生命周期的成本；塞进 SIEM 的查询语言，则往往在表达力上碰壁——时序链、缺失检测、实体建模，不少是语言层根本没有的原语。

WarpFusion 想走的是中间那条路：**用一个二进制跑完完整关联链路，用一门语言把"要找什么"说清楚**。

---

## 二、它是什么

WarpFusion 是一个用 Rust 编写的**实时关联计算引擎**。它的能力内核是**跨多条事件、跨时间窗口的模式匹配**，而不是单条过滤——输入结构化事件流，输出满足关联条件的、可解释且带评分的结果：可以是告警，也可以是结构化数据。

对外它是一个**单二进制、零外部依赖**的引擎 `wfusion`，配套 `wfl`（规则开发）与 `wfgen`（测试数据生成），开箱即用。既能在单机跑通完整链路，也设计了声明式窗口分布（`partitioned` / `replicated` / `local`）以平滑扩展到多节点。

## 三、WFL：用五原语说清"要找什么"

规则用 **WFL**（WarpFusion Language）编写，采用职责分离的**三文件模型**：

| 文件 | 职责 |
|---|---|
| `.wfs` | 数据长什么样：窗口定义、字段 schema、时间字段 |
| `.wfl` | 匹配什么模式：事件绑定、时序匹配、评分、输出 |
| `.toml` | 怎么跑：source、sink、窗口内存、watermark |

语言的核心是**五个原语**，所有语法糖在编译期归一为唯一语义内核：

- **Bind** —— 把事件流绑定成带条件的别名；
- **Match** —— 时序序列、无序共现、双阶段匹配、缺失检测；
- **Stats** —— 声明式窗口统计聚合；
- **Join** —— `snapshot` / `asof` / `anti` 关联与上下文富化；
- **Yield** —— 带契约的结构化输出。

![WFL 五原语 Core IR](../images/wfl-five-primitives.svg)

所有语法糖在编译期**归一为这唯一语义内核**——这意味着语言扩展不会拖累执行路径：新增的表达能力最终都落到同一套执行原语上，而不是堆叠特例。

### 例一：多步攻击链（时序链）

```wfl
rule chain_attack {
    events {
        scan  : conn_events && action == "syn"
        login : conn_events && action == "login_fail"
    }
    match<sip:30m> {
        on event {
            scan  | count >= 5;
            login | count >= 3;
        }
    } -> score(90.0)
    entity(ip, scan.sip)
    yield network_alerts (sip = scan.sip, alert_type = "chain_attack")
}
```

同一 IP 在 30 分钟窗口内既扫描了 5 个端口、又失败登录 3 次——命中，评分 90，结果归属到 IP 实体。

### 例二：缺失检测（A → NOT B）

```wfl
events {
    fail : auth_events && action == "failed"
    ok   : auth_events && action == "success"
}
match<sip:10m> {
    on event { failed: fail | count >= 3; }
    and close { succeed: ok | count == 0; }
}
```

"失败 3 次，且到窗口关闭为止**一次都没成功过**"——`and close` 让"没有发生"成为一等判断条件。这是很多查询语言需要绕子查询甚至外部模块才能表达的语义。

### 例三：声明式窗口统计

```wfl
rule traffic_stats {
    events { c : conn_events }
    stats<1h:fixed> group by (c.sip) {
        c | count        as hits;
        c | sum(c.bytes) as total_bytes;
    }
    entity(ip, c.sip)
    yield traffic_stats (
        sip   = c.sip,
        hits  = stat.value(final(hits)),
        bytes = stat.value(final(total_bytes))
    )
}
```

一个原语覆盖"每小时每源 IP 的流量画像"。同一套语言既能写逐事件流式检测，也能写声明式窗口统计。

### 语言层的差异化能力

以下几项是 WFL 的**语言一等公民**，而非靠平台能力或外部模块补齐：

| 能力 | 说明 |
|---|---|
| 时序链 + OR 分支 | 多步序列、步间时间约束、否定步、分支组合 |
| 双阶段匹配 | `on event` 实时求值 + `on close` / `and close` 窗口关闭求值 |
| 缺失检测 | "该发生的没发生"作为原生判断 |
| 一等实体声明 | `entity(type, id)` 把结果归属到实体，驱动跨规则评分累加 |
| 数值评分 | `-> score(expr)`，安全是风险、运营是严重度或置信度 |
| 稳定统计上下文 | `stat.*` 把"为什么触发"变成可输出的证据字段 |

横向对照主流检测 DSL：在 YARA-L / EQL / Sigma 面前，WFL 的表达力高出一个量级（时序链、双阶段匹配、实体建模、评分这些都是它们的语言层空白）；相对 SPL / KQL 这类通用查询语言，差距已从"远弱"收窄到**通用函数库丰富度**这一设计边界——与 SPL Top50 高频函数的对齐率已达 100%（50/50），并额外覆盖安全检测专有族。

## 四、为什么快：五个杠杆

性能不是调出来的，是砍出来的。

| 杠杆 | 砍掉了什么 |
|---|---|
| **列式批式向量化** | 逐事件对象分配 + 解释器分发 |
| **数据零拷贝** | Event → Record → DataRecord 的多层拷贝 |
| **内存精确控制** | 窗口数据仅过期且被下游全部消费后才释放；数据预读总量设上限 |
| **Rust vs Java** | JVM GC 停顿 |
| **规则即规划** | 运行期逐事件解释（Stats / Match 编译期定型为执行计划） |

其中"内存精确控制"是设计纪律而非优化技巧：窗口数据只有在**既已过期、又被所有消费者确认消费**之后才释放，配合预读字节预算，内存占用是**可预测、可规划**的，而不是"跑着看"。

## 五、性能：NEXMark 全查询对照

先看口径，再看数字。

**测试条件**：100M 条事件、in-memory 源 + blackhole 汇、Linux 8 核（与 VVR **同型号云服务器**）、引擎 v2.0.7、21/21 套件查询端到端 clean 跑批。对照组数据来自阿里云《Nexmark 性能白皮书》发布的 OSS Flink 与实时计算 Flink（VVR）。

| 对照基线 | 几何平均领先 | 算术平均领先 | 逐查询区间 |
|---|---|---|---|
| **Flink OSS**（3×12 vCPU / 48GiB） | **24.3×** | 44.7× | 6.06× – 231.49×（20/20 全面领先） |
| **阿里 VVR**（8 CU / 32GiB 托管集群） | **6.8×** | 10.1× | 1.76× – 39.98×（20/20 全部达 VVR） |

![WarpFusion vs Flink NEXMark 对照](../images/vs-flink.jpg)

作为参照，白皮书口径下 VVR 相对 OSS 本身的提升是 **3.24×**（报告按 20 个查询复算为几何 3.57×）。也就是说，WarpFusion 是在一个已经做过企业级优化的商用引擎之上，再领先一个身位。

**逐查询节选**（EPS/RPS 单位：条/秒）：

| Query | 语义 | WarpFusion | OSS | VVR | vs OSS | vs VVR |
|---|---|---:|---:|---:|---:|---:|
| q1 | 无状态投影 | 16.85M | 1.75M | 4.38M | 9.62× | 3.85× |
| q7 | 时段最高出价（match 序列） | 9.29M | 0.08M | 0.30M | 116.74× | 31.03× |
| q9 | 中标出价（asof join） | 7.96M | 0.04M | 0.38M | 185.08× | 21.22× |
| q11 | 用户会话统计（session 窗） | 10.85M | 0.24M | 0.69M | 44.36× | 15.84× |
| q19 | 拍卖 Top-10（stats） | 7.86M | 0.17M | 1.05M | 46.08× | 7.48× |
| q20 | 展开关联（snapshot join） | 17.27M | 0.07M | 0.43M | **231.49×** | **39.98×** |
| q14 | 时间戳换算（Calculation） | 8.80M | 1.45M | 5.00M | 6.06× | **1.76×** |

**为什么头条用几何均值**：逐查询倍数分布严重右偏——约一半查询落在 1.76×~7.15× 的典型区间，但 q7 / q9 / q11 / q16 / q20 等明星查询形成长尾。对"提速倍数"这种比率量，几何均值更稳健，也更诚实：它回答的是"随便挑一个查询，大概快多少倍"。算术均值（10.1×）则被少数离群值抬高约 1.5×，仅作上限语境。

**边缘项与已知问题**（一并公开）：

- **q14 是相对 VVR 最弱的一项（1.76×）**：Calculation 类、字符串处理重，瓶颈在引擎行式 cell 求值，改进需进运行时做列式字符串求值，已列为通用能力独立立项。
- **q18 内存（RSS 27.9GB）为已知问题**：100M 状态窗随数据量线性增长。
- **q5 / q18 存在规模退化**（30M→100M 分别 0.58× / 0.34×）：均由窗口状态随数据量增长驱动，属预期内的状态型特征，非 bug。

**吞吐口径说明**：上文全部数字均为 **NEXMark 单查询口径**——Linux 8 核、**blackhole 汇（不落告警）**、2026-08-27 权威跑批，代表纯算力上限。

> ⚠ **多规则混合负载目前没有可用的近期实测数据**。历史上存在一次测量（6 条规则、macOS 4 并发），但测于 2026-08-10，早于 08-16 落地的批式向量化等重大吞吐优化，**已过时且未复测，故不引用**。
>
> 实际部署若规则大量触发告警并落 sink，吞吐会低于上述 blackhole 口径——容量规划请按自身告警率实测。

> ⚠ **边界声明**：上述领先是在"引擎纯算力 / 单机内存"这一隔离维度上测得的。WarpFusion 当前为**单机 8 核、纯内存、无 exactly-once / checkpoint / 分布式协调开销**；NEXMark 是合成基准，结论作**能力参照**而非生产 SLA 承诺。生产级容错、分布式与有状态一致性补齐后，才能做对等比较。

## 六、规则自带测试：从"写完祈祷"到"写完验证"

规则语言的成熟度，一半看表达力，一半看能不能验证。WFL 把测试写进规则文件里：

```wfl
test full_chain for chain_attack {
  input {
    row(scan, sip = "10.0.0.1", ... action = "syn",        event_time = "2026-01-01T00:00:00Z");
    row(login, sip = "10.0.0.1", ... action = "login_fail", event_time = "2026-01-01T00:00:05Z");
  }
  expect { hits == 1; hit[0].score == 90.0; hit[0].entity_id == "10.0.0.1"; }
}
```

配套的完整闭环：

- `wfl test` —— 内联契约测试，一键验证命中 / 未命中两条路径；
- `wfl replay` —— 用历史数据离线回放；
- `wfl verify` —— 新规则产出与原规则逐字段对拍；
- `wfgen` —— 用 `.wfg` 场景文件生成带**命中 / 近失 / 未命中**三类样本的数据流。

**AI 时代，规则开发的差距在哪？** 判断一门语言对 AI 是否友好，看的不是"语料多不多"，而是三件事：**语言表面积**（越小越易一次生成正确）、**语义明确度**（越显式歧义越少）、**验证反馈速度**（越快越能形成"生成→验证→修正"闭环）。

WFL 恰好三项都占优：一条规则**几行**声明式代码、`entity`/`score`/`match` 语义显式、写完 `wfl test` **秒级**验证命中与未命中。实践上的结果是——规则可以完全交给 AI 生成，人只负责审核与验收。反观 Flink，即便 AI 秒出 `MATCH_RECOGNIZE` 或数百行 Java，"能不能正确运行"仍要等到 job 部署之后才知道，且大量隐式约定（状态、水位、并行度、序列化）放大了出错面。

**AI 把"编写"变成了低成本动作，于是验证与上线成为规则迭代周期的决定项**——WFL 在这两处有结构性优势（内联契约测试 + 热加载）。

> 需要守住的边界：**AI 生成不等于免验证**。检测规则出错是静默的（漏报/误报不报错），生成的规则必须跑 `wfl test` 并纳入回归。项目为此提供 `wf-skills` AI 技能包（装进 `~/.claude/skills` / `~/.codex/skills`，6 个技能、1300+ 行指引）、`wf-rules` 真实规则库作语料，以及 LSP 在编辑器内即时校验。

## 七、算一笔账：综合使用成本

吞吐只是其中一项。落到团队真正要付的账上，差距主要在三处：

| 成本项 | Apache Flink | WarpFusion |
|---|---|---|
| 硬件 | 至少 2–3 个节点（JobManager + TaskManager + Kafka）+ 磁盘状态存储 | 1 台 8GB 节点即可起步 |
| 中间件 | Kafka + checkpoint 状态存储等额外组件 | 零外部依赖 |
| 运维人力 | 专职流工程师维护集群、调 checkpoint / state | 单二进制，普通运维即可 |
| 开发人力 | 数据工程师写 Java / SQL，每条规则一次 job 生命周期 | 分析师写 WFL，热加载生效（AI 可辅助生成） |
| 规则迭代 | AI 可加速**编写**，但**验证 + 编译 + 部署 job** 的周期不变 | 编写 → 内联契约测试 → 热加载，端到端链路最短 |
| 授权 | 开源免费；托管服务按小时计费 | ELv2：企业内部自用免费，转为对外服务需商业授权 |

对**单机可承载、千条规则**这一常见规模，Flink 的综合成本（硬件 + 运维 + 开发）通常是数倍：资源预算差 2–3 倍，运维和开发还要养不同类型的人，规则迭代再慢一个量级。而这恰恰是绝大多数企业实时检测场景的真实规模。

**量级**：以千条规则、十万级 EPS 的中等平台估算（含硬件、中间件与人力，按公开行情粗算），Flink 自建落在**百万量级**（约 55 万/年，3 年约 165 万），WarpFusion 落在**十万量级**（约 14 万/年，3 年约 42 万），**差距约 4 倍**。

更关键的是结构：Flink 侧硬件仅占约 27%、**人力占约 73%**——真正的降本杠杆是摆脱对专职流工程师的依赖，而不是省服务器。完整的成本模型与可调假设见[竞争力白皮书](./warp-fusion-competitiveness.md) §5.1。

## 八、用在哪

NEXMark 的 Q1–Q22 覆盖的流处理形态，正好映射到四类真实场景：

| 场景 | 对应的引擎能力 | 典型负载 |
|---|---|---|
| **SIEM / 安全检测** | 序列匹配、行为统计与 Top-N、上下文关联 | 攻击链检测、告警归并、实体行为分析 |
| **风控反欺诈** | 每实体最后状态、Top-N、速率窗口 | 名单匹配、异常排行、实时频控 |
| **AIOps / 可观测** | 滑窗 / 会话窗突增、处理时间频控 | 指标异常、限流去重 |
| **实时数仓 / ETL** | 投影、过滤、富化、落盘 | 字段归一化、日志标准化、热冷分层 |

## 九、上手

```bash
git clone https://github.com/wp-labs/warp-fusion.git
cd warp-fusion && cargo build --release
```

```bash
# 1. 内联测试 —— 验证规则逻辑
wfl test rules/port_scan_whitelist.wfl --schemas "schemas/*.wfs"

# 2. 离线回放 —— 用历史数据验证
wfl replay rules/port_scan_whitelist.wfl --input data/conn_events.ndjson

# 3. 引擎运行 —— 完整管道
wfusion run -c ./wfusion.toml
```

仓库内可直接运行的示例：`port_scan_whitelist`（端口扫描 + 白名单）、`ssh_brute_force`（SSH 爆破）、`sqli_probe`（SQL 注入探测）、`rat_propagation`（远控扩散，多步扫描→登录→外传）。

数据接入侧支持 **Arrow IPC over TCP** 直连——从上游解析引擎到规则引擎全程免解析、类型保真。

## 十、诚实的边界

不做过度承诺，是这个项目的一贯口径：

> **弱势项的标准（与竞争力白皮书一致）**：只有"该维度上 WarpFusion 低于 Flink（Flink 有/更强，我们无/更弱）"才算相对 Flink 的弱势项；"自己内部相对最弱的项"（如 q14 仍领先 Flink）不算弱势项。下表只列现状，不把内部相对弱项混称为短板。

| 维度 | 现状 |
|---|---|
| **容错** | 当前 best-effort，**无 exactly-once / checkpoint**（可靠性在路线图） |
| **规模** | **单机吞吐不是瓶颈**——8 核实测单查询 200 万–3100 万 EPS（NEXMark / blackhole 汇口径）；真正的边界在多节点高可用与分布式容错。告警密集场景的容量需按自身告警率实测 |
| **生态广度** | Flink 十年积累的**数百个**社区 connector 仍是护城河。WarpFusion 有**基于注册表的 connector 体系**（`wp-connector-api` + `wp-core-connectors` + `wp-connectors`，可外部注册扩展），已覆盖 **Kafka、MySQL、PostgreSQL、Doris、Elasticsearch、ClickHouse、VictoriaLogs、VictoriaMetrics、Prometheus、HTTP、UDP** 及 file / tcp / syslog 等主流通道；日志解析归一化由上游 WarpParse 的 WPL/OML 适配器承担——差距在**广度**（尤其 SaaS 与小众数据源），不是没有体系 |
| **内存** | q18 类状态窗在大数据量下的内存增长为已知问题 |
| **通用计算** | 三角函数、行保留聚合（eventstats 类）等不在主战场，交下游 SIEM |

**选型建议**：如果你的需求是**跨事件 / 跨窗口关联、规则需要高频迭代、负载在单机可承载范围内**，WarpFusion 是正好的工具——一个二进制跑完，规则几行写完、自带测试闭环。真正的分水岭不在吞吐，而在**是否需要多节点高可用与 exactly-once / checkpoint**：若需要，请诚实地回到 Flink。
